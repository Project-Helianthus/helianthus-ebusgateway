## Recovery checkpoints refuse assets with several sources

The internal recovery checkpoint holds one source per asset, so it now refuses what it cannot represent instead of dropping a contributor's state. Exporting a hub that holds an asset with a declared contributor fails closed with the named error `ErrRecoveryMultiSource` and yields the zero record, which no restore accepts; `ExportRecoveryChecked` reports that reason, while `ExportRecovery` keeps its signature. Restoring a checkpoint that names a second source for an asset (a second entry, an accepted batch, the retained control or an epoch event covering the asset), or restoring into a hub whose asset declares a contributor, is refused as a whole with the same error, closes every declared asset and installs nothing (#1539). The recovery seam has no production user, so no stored state changes; a contributor-aware record will be defined before the seam is first used in production. The version 1 record and its bytes for single-source hubs are unchanged, and no published output, golden, identifier or wire value changes. The gateway binary changes, so affected release evidence must be renewed before the final bill of materials freeze.
