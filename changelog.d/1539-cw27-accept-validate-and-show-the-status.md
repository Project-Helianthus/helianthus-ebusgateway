## Accept, validate and show the status of operator records in the Portal configuration

The Portal configuration store gains an optional operator-record section (`internal/portalconfig/operator_records.go`) with three forms of operator declaration: an operator-slot anchor, a configured relation and a pairing of two views. A replacement is validated against the element catalog compiled into the SemReg graph package before anything is written, and a refusal names the failing field with a closed code for an invalid starting or far end, an unknown relation definition, a basis class the definition does not admit, an unknown resource kind, an invalid anchor or pairing, and a duplicate resource, anchor or relation key. The section is persisted in the same store root under the same writer and atomic replacement, as its own file with its own revision; it is absent until the first non-empty section is accepted, so stored configuration records load unchanged. The configuration route reads and replaces it with `?section=operator_records`, and the configuration view carries it only when it holds records. The gateway runtime feeds the accepted section to the configuration provider grouped by home asset and shows each record as `published`, `waiting` (home asset not declared or not open to the provider, or starting end not yet published) or `refused` with the kernel's stable error; waiting records are retried after every later hub publication. `docs/architecture/portal-config-sharing.md` describes the section (#1539).
