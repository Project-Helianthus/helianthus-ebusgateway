## AdapterMux hold for an adapter that runs one host command behind

The AdapterMux now detects an adapter that runs one host command behind. A START cycle runs from one START request to the next; three consecutive START cycles without an in-step answer and without a completed transaction are a detection. A cycle counts as bad when, before the next START request, a STARTED names another initiator than the pending one, an answer never came before the stale-answer barrier gave up, or a second STARTED arrives with nothing pending. A completed transaction or an answer the barrier consumed ends the run.

The first detection resets the adapter link once: the mux closes its adapter connection, reopens it and repeats INIT; under the eBUS driver this replaces the driver generation. A further detection holds active arbitration: no START request is sent, gateway reads end at their usual admission bound with an error naming the hold, external clients' START requests stay unanswered, and passive reception continues. The reason `adapter_out_of_step` appears in the log (`adaptermux: adapter_out_of_step bad_start_cycles=3 action=link_reset`, `adaptermux: active_arbitration_hold state=set reason=adapter_out_of_step bad_start_cycles=3`), in `bus_summary.status.degraded.reasons` (GraphQL and MCP) and as the gauge `ebus_adaptermux_active_arbitration_held`. The hold ends when the adapter reports a reset or the link reconnects (`adaptermux: active_arbitration_hold state=cleared trigger=adapter_reset|reconnect|close`), and the single reset is available again after the next completed transaction. Healthy, slow and contended adapters are not detected in the offline fixtures.

After an abandon-watchdog release, a STARTED with no pending request is treated like a cancelled selection: it is counted as undeliverable and is not an out-of-step answer.

START deadline, barrier, abandon, grace and cap timings, the grant order and the configuration surface are unchanged; existing log lines are unchanged. The gateway binary changes and this is adapter-direct transport work: the affected adapter-direct rows must be re-run in the consolidated hardware session, and the affected release evidence must be renewed before the final bill of materials freeze.
