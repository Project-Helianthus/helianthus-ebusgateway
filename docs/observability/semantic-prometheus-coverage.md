# Current /metrics inventory and coverage limits

The complete declared renderer inventory below accompanies the partial capability coverage audit for [issue #1005](https://github.com/Project-Helianthus/helianthus-ebusgateway/issues/1005), not closure of its original acceptance checklist. **Proven** below means established by the current source renderer; **Hypothesis** means a proposed interpretation or future design; **Unknown** means evidence is missing. These evidence grades are separate from qualification, admission, freshness and physical acceptance. Nothing here promises stability before Helianthus 1.0.

The public [native transport and semantic coverage contract](https://github.com/Project-Helianthus/helianthus-docs-ebus/blob/main/deployment/prometheus-semantic-coverage.md) owns the coverage boundary. This page inventories gateway exposition; it introduces no protocol facts, decoder meaning, acquisition or electrical capability. Native drivers retain native evidence and qualification. SemReg owns promoted protocol-neutral projections; the gateway composes them.

There are 13 Thermal and 19 Infrastructure fields. Sixteen slots per domain give at most 208 Thermal plus 304 Infrastructure value samples and the same 512 availability samples (1,024 combined per target). A binding has at least one field, exactly one dimension, a unique domain/slot and a unique composite tuple of domain, asset ID, source ID, source epoch ID, binding ID, driver generation, service instance and dimensions. Slot, fields and retired status are excluded from that composite tuple; the same source/service may therefore appear in different slots with different dimensions. Unknown, duplicate or cross-domain fields and invalid/out-of-range slots fail registry validation. At most 32 distinct assets can be selected for capture. Retired slots remain reserved by contract; the renderer does not allocate or persist them.

Only configured fields get availability samples. A validated, non-retired binding with a current matching source epoch and driver generation, qualified/available service and read capability, exact projection, a single non-conflicting qualified/promoted/good candidate, fresh matching evaluation and a valid finite converted value emits availability `1` and its value. Unvalidated, retired, unavailable, stale, malformed or withheld selections emit availability `0` for configured fields and omit their numeric values; an invalid registry fails composition. Zero is a legitimate measurement only when admitted. Unconfigured fields produce neither availability samples nor value metadata. A failed capture/view withholds values without reusing a previous scrape or acquiring native data; valid sibling selections survive field-specific rejection. This is an export rule, not permission to erase upstream per-field last-known-good evidence.

Production uses an empty registry, so the configured upper bounds above are implementation capacity, not currently exported production values. Durable publication, restart revalidation and retired-slot reservation remain the owner work in [#1341](https://github.com/Project-Helianthus/helianthus-ebusgateway/issues/1341). Native CAN composition remains separate. eeBUS output belongs to `helianthus-eebusreg`; it is not implied by gateway lifecycle status. Existing eBUS MCP envelopes, deterministic goldens and GraphQL parity are unchanged.

## Acceptance limits

**Proven:** manual reconciliation of current renderers establishes this inventory and the omission rules. **Hypothesis:** future native CAN observations can feed a bounded host exporter once native contracts and composition are accepted. **Unknown:** actual deployed values, electrical timing/capability, physical transport behavior, device qualification and final-candidate acceptance. No hardware observation follows from source inspection. Full committed-change CI, independent review and applicable transport/passive classification remain separate acceptance work; this document does not close #1005 or introduce alert rules.

## Complete composed route inventory

**Proven** here means source renderer support. This source-based inventory is not
an observed scrape, production measurement, health assessment or qualification.
The structured companion is [metrics-inventory.json](https://github.com/Project-Helianthus/helianthus-ebusgateway/blob/main/docs/metrics-inventory.json).
The table lists all 106 declared families, including the 32 dynamic field-table
families above. Its owner page is this page for every row; the source column links
to each implementation owner. The linked transport and semantic contracts above
retain their interpretation boundaries. Metric renaming is outside this inventory.

The HTTP server registers the configurable metrics mount only with a bus
observability store. The handler renders that store first, then the shared-hub
Thermal/Infrastructure renderer, then Huawei transport events. The store invokes
runtime status (which invokes baud availability), optional detached PV/storage/EVSE
semantic metrics and its own observation writers. The standalone
[semantic text helper](https://github.com/Project-Helianthus/helianthus-ebusgateway/blob/main/semantic_prometheus_text.go) calls that same detached
semantic renderer; it does not add another family to the composed route. There is
no automatic expvar, Go runtime or process collector forwarding on this route.

The dynamic paths are finite: the detached semantic emitter forwards its declared
eight gauge names; Thermal/Infrastructure iterates the field-to-name table and
uses each row's name in value HELP, TYPE and slot samples, alongside the fixed
availability family. Huawei's formatted sample uses a fixed family name. The
source guard parses these writer calls and the field table, checks the dynamic
format sites and detects changed renderer call dependencies requiring retracing.
Unaccounted dynamic output blocks the inventory claim.

In the table, labels are renderer keys; `connector` is optional on detached
semantic fact families and appears only for allocated-current connector slots.
No scrape-added deployment labels are included. Disabled domains, missing map
entries, unknown observations, declared-but-unbound fields and admitted numeric
zero remain distinct. A semantic failure withholds that section's values without
replacing valid native or sibling last-known-good evidence. Production binding
statements describe composition, not a live target.

## Adapter telemetry is expvar-only

These declarations are served as expvar JSON at `/debug/vars`, not Prometheus
text at `/metrics`. Their names do not establish Prometheus types. No forwarding
writer was found in the composed route. They are distinct from the rendered
`ebus_adaptermux_*` diagnostic counters and gauge in the table.

[Adapter declaration source](https://github.com/Project-Helianthus/helianthus-ebusgateway/blob/main/cmd/gateway/semantic_vaillant_adapter_info.go)
and [route registration](https://github.com/Project-Helianthus/helianthus-ebusgateway/blob/main/cmd/gateway/gateway_http_control_plane.go) own this
separation. The offline guard checks structured inventory, page rows, writer
syntax, finite dynamic field expansion, types, label keys and route composition.
Its independent negative controls remove a rendered family, promote an expvar
value, change a type, omit enablement, change labels and remove a dynamic field.
It does not start a server or infer physical transport health. Scrape-based
acceptance remains separate from this source proof. Existing eBUS MCP compatibility
and GraphQL parity contracts are unchanged.
